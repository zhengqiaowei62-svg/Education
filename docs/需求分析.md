# 需求分析（Requirements）

> 版本：v2.0 · 与当前代码同步（backend/ + frontend/）

## 1. 背景

医学专业生需同时阅读多本教材（生理学、组织学、解剖学等），各书章节顺序、术语命名、知识深度不一致，学生面临：
- 同一概念在多本书的描述需要**比对**才能完整；
- 教师备课需输出**统一脉络**而非简单堆叠；
- 复习问答需要**可追溯**到具体页码与原文，不能"AI 幻觉"。

本系统的目标是：**自动从多本教材抽取知识点 → 跨书对齐与合并 → 形成统一图谱 → 支撑可追溯问答**，并允许教师以自然语言**人工干预（HITL）**结果。

—

## 2. 用户角色

| 角色 | 主要诉求 |
| --- | --- |
| 学生 | 用对话方式问问题，看到融合视角的答案与可点击的原文出处 |
| 教师 | 上传教材、整合图谱、修订（合并/拆分/重命名）、导出整合报告 |
| 教研管理员 | 看 Token 成本、图谱规模、检索基准、是否能压缩冗余 |

—

## 3. 关键概念定义

### 3.1 知识点粒度

定义最小可索引单元为"**知识节点**"，分类（与代码 `KGNode.category` 对齐）：
- `核心概念`（如「动作电位」）
- `定理`（如「Donnan 平衡」）
- `方法`（如「记录技术」）
- `现象`（如「超极化」）
- `图像区块`（来自 PDF 版面解析的图/表）

判断粒度：**一个节点应能被单句定义**，且至少出现在一本教材的某段独立讨论中（≥80 字符或被 vision 模型识别为图块）。过细 → 噪声；过粗 → 失去对齐价值。

### 3.2 重复 / 等价判定

由 Judge Agent 在融合阶段决策。证据组合（按权重排序）：
1. **名称完全相同** + 类别一致 → 直接合并（前置规则）；
2. **名称别名/变体**（如「静息电位 / Resting potential」）→ Judge 对照 definition 余弦/语义判断；
3. **definition 高度相似**（embedding 余弦 ≥ 0.85）+ 至少一项共同邻居关系 → Judge 确认；
4. 其它情形 → 保持为不同节点，但允许加 `parallel` 边表达"对应关系"。

冲突处理：当 Judge 不确定时输出 `pending` 决策，进入 HITL 待办，由用户复核。

### 3.3 教学连贯性

衡量"整合后的图谱是否符合教学顺序"。运营指标：

$$
\text{Coherence} = \frac{\#\,prerequisite\,边\,符合\,章节序的}{\#\,prerequisite\,边\,总数}
$$

期望阈值：**≥ 0.80**。每次融合后写入 `report/整合报告.md`。

### 3.4 压缩比

$$
\text{CompressionRatio} = 1 - \frac{|\,V_{\text{merged}}\,|}{\sum_b |\,V_b\,|}
$$

其中 $V_b$ 是第 $b$ 本书的节点集合。代表"整合消除了多少冗余"。当前系统在 7 本医学教材上目标 **≥ 0.35**（即至少压掉 35% 重复）。

### 3.5 分块（Chunking）策略

后端 `backend/core/rag_pipeline.py`：
- **滑动分块**：按 `RAG_CHUNK_SIZE`（默认 480）字符 + `RAG_CHUNK_OVERLAP`（默认 80）滑窗；
- **章节优先**：若 PDF 解析输出包含 `chapter` / `page` 元数据，则**先按章节分割**再滑窗，避免跨章拼接；
- **图像区块**：MinerU 区块独立成 chunk，metadata 携带 `bbox`，问答时可定位到坐标。

## 4. 功能性需求（FR）

| ID | 需求 | 当前实现 |
| --- | --- | --- |
| FR-1 | 上传 PDF（≤ 200MB / 文件） | `POST /api/upload`（multipart） |
| FR-2 | 列出 / 删除已上传教材 | `GET/DELETE /api/textbooks` |
| FR-3 | 单书知识图谱抽取 | `POST /api/graph/extract`（Extractor Agent） |
| FR-4 | 多书图谱融合 | `POST /api/graph/merge`（Judge Agent） |
| FR-5 | HITL 自然语言修订（split/rename/delete/merge/add_edge/remove_edge） | `POST /api/graph/modify` |
| FR-6 | 图谱多视图：力导向 / 知识树 / 自由画布 / 矩阵热力 | `frontend/src/views/GraphView.vue` |
| FR-7 | 图上拖拽合并 | Shift+drag 触发 `mergeNodesByDrag` |
| FR-8 | 全文 / 向量 / 区域 三通道检索 + RRF + Rerank | `rag_pipeline.retrieve` + `_rerank` |
| FR-9 | 多轮对话历史注入 | `RagQueryRequest.history` |
| FR-10 | 答案附原文出处 | `Citation` schema + `/api/rag/source/{id}` |
| FR-11 | LLM Token 用量统计 | `/api/stats/tokens` |
| FR-12 | RAG 基准评测 | `/api/stats/benchmark` |
| FR-13 | 整合报告导出（md / PDF） | `/api/report/download` `/api/report/pdf` |
| FR-14 | 本地模型推理（Ollama） | `LLM_PROVIDER=ollama` 路径 |
| FR-15 | Docker 一键部署 | `docker compose up -d --build` |

—

## 5. 非功能性需求（NFR）

| 维度 | 指标 |
| --- | --- |
| 响应时间 | 检索类 P50 < 600ms（已 chunk + cosine 实现）；问答端到端取决于 LLM |
| 可追溯 | 每条引用必须能映射到 `chunk_id` 并能渲染原文 |
| 可重放 | LLM 调用失败回退、Token 计数即使无 SDK usage 也估算 |
| 可移植 | 一份 `.env`，云端 / 本地 Ollama 切换无需改代码 |
| 可观测 | 仪表盘提供 4 类核心指标（Token / 图谱 / 基准 / 报告） |
| 可扩展 | 路由与 pipeline 解耦；新增检索通道只需扩 `channels` 列表 |
| 安全 | API Key 仅从环境变量读取；CORS 默认 allow-all（生产需收紧） |

—

## 6. 数据规约

### 6.1 教材
```jsonc
{
  "textbook_id": "tb_xxx",
  "title": "生理学（第 9 版）",
  "chapters": [{ "title": "...", "page_start": 1, "page_end": 24, "blocks": [...] }],
  "raw_path": "uploads/xxx.pdf"
}
```

### 6.2 图谱
```jsonc
KGNode  = { id, name, category, definition, textbook_id, page, ... }
KGEdge  = { source, target, relation_type, evidence }
```
关系类型：`prerequisite | parallel | contains | applies_to`。

### 6.3 修改记录（HITL 审计）
```jsonc
ModificationRecord = { ts, action, instruction, payload, applied: bool, message }
```

—

## 7. 边界与不做的事

- 不做 OCR 误差校正（依赖 MinerU 输出质量）。
- 不存关系数据库；当前 in-memory + JSON 落盘已足够 MVP。
- 不做用户系统/权限；所有数据全局共享。
- LLM 调用失败时的"知识 fallback"会以**结构降级**而非"编造"，宁缺毋滥。

—

## 8. 验收标准（基于代码可复现）

1. 上传 ≥ 2 本 PDF，调用整合后 `Coherence ≥ 0.80`，`CompressionRatio ≥ 0.35`；
2. `tests/smoke_rag.py` 全绿；
3. `POST /api/stats/benchmark` 返回 `hit_rate ≥ 0.6`（默认样本）；
4. 仪表盘 Token 数据非零（提交一次问答之后）；
5. `docker compose up` 后 `http://localhost:8080` 可上传、抽取、问答全流程跑通。
